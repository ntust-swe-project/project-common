# 期中專題 起始文件（v1.0 定案版）

## 文件說明

本文件是三個子組（Waterfall + AI、Agile + AI、AI-Agent）共同的唯一輸入，定案後各組再用自己的方法做需求分析。

這份文件只描述「要做什麼、為什麼做」，不描述「怎麼做」。具體機制、數值、建築、平衡細節，都是各組需求分析的產出，不寫在這裡。

本版已納入 2026-11-07 組內討論的結論，並作為共用 repo（`project-common`）的第一個 commit。

**標記說明**

| 標記 | 意思 |
| --- | --- |
| 【決議】 | 組內已有共識的項目 |
| 【方向】／【決議，方向】／【決議，只定方向】 | 方向已有共識，具體做法由各組決定 |
| 【決議，待各組判斷】 | 是否採用由各組自行決定 |
| 【提案，待三組確認】 | 本版新提出、尚未經三組同意的項目。確認前各組以此為工作假設，確認後改標【決議】 |

## 1. 願景【決議】

在一座危機不斷升級的太空站上，玩家間接指揮一群各有狀態的殖民者，透過建造與自動化讓太空站運作下去，撐過一波比一波嚴峻的危機。

一場遊戲有明確的結束，可以一次玩完。

## 2. 類型與參考【決議】

類型是殖民地生存經營（colony sim），主要參考《缺氧》（Oxygen Not Included），但不是複製。

我們參考的是它的**體驗**：間接控制、殖民者有自己的狀態、系統之間互相牽動。不沿用它的系統設計、名詞與數值。

| 項目 | 缺氧 | 本專題 |
| --- | --- | --- |
| 場景 | 地底小行星 | 太空站 |
| 節奏 | 沙盒，一場可玩數十小時 | 一場 30 個遊戲天，約 30 分鐘 |
| 壓力來源 | 系統自然崩潰 | 逐波升級的危機 |
| 結束條件 | 無，玩家自己決定 | 有，見第 7 節 |

討論中也提到另外兩個參考點，列在這裡供各組理解我們想要的「結束感」：

- 《Cities: Skylines》：以經營失敗（如破產）或指標未達標作為結束，而不是靠倒數計時
- 《Mini Metro》：單一明確的崩潰條件（車站爆滿）就足以製造全程壓力

各組 review AI 產出時，若內容只是在重現上述任一款遊戲的設計，應視為 AI-invented requirement 並記錄。

## 3. 核心體驗【決議】

遊戲要讓玩家感受到以下四點。這些是體驗目標，具體怎麼實現由各組分析。

1. **殖民者有個體狀態**：玩家照顧的是一個個「人」，不只是資源數字。殖民者之間是合作關係。
2. **間接控制**：玩家下指令、定優先順序，殖民者自己決定怎麼執行。
3. **建造與自動化**：玩家透過建造設施、建立自動化，減輕管理負擔並應對危機。
4. **逐波加壓**：危機以波次出現且越來越嚴重，是遊戲主要的壓力來源。

**已知的設計張力**（不在這裡解決，留給各組分析）：

- 自動化是「先投入、後回本」，一場只有 30 天，回本來不來得及發生？
- 間接控制有延遲，危機來得快的時候，這個延遲是挑戰還是挫折？
- 第 4 節的「動態調壓」會讓每一場的數值都不一樣，怎麼驗證「每天都有壓力、第 30 天前後收束」？
- 失敗條件如果有多條（第 7 節），新手可能在第 10 天就結束，這和「一場 30 分鐘」的目標會互相拉扯。

## 4. 節奏與目標

### 4.1 一場遊戲的長度【決議】

玩家的目標是撐過 30 個遊戲天的危機。

- **時間單位是「天」**：遊戲內以天為單位推進，危機波次掛在天數上。【決議】
- **30 天 ≈ 約 30 分鐘真實時間**：30 分鐘是體驗目標，30 天是達成它的結構。每天實際多長由各組決定（量級上約 1 分鐘），不是硬性規則。

### 4.2 軟限制【決議】

- **軟限制的意思**：不用倒數計時強制結束，而是讓危機逐漸增強，使一場遊戲自然地在第 30 天前後收束。
- **玩家感受到的是壓力，不是時鐘**：玩家應該在意「下一波擋不擋得住」，而不是「還剩幾分鐘」。
- 小幅偏差可以接受，各組可自行訂定可接受的範圍。

### 4.3 每天都要有壓力【決議，方向】

目標是從 day 1 到 day 30 每天都有一點壓力，而不是前期無事、後期暴死。討論中提到兩個可行方向，記錄於此供各組參考，**但不指定做法**：

- 每個危機設一個硬門檻作為保底
- 每天評估玩家的發展速度，據此微調隔天的壓力（例如玩家在某項設施上進度落後，就讓對應危機的成長放緩）

採用哪一種、或兩者併用、以及如何觀察玩家行為，都是各組需求分析與設計的產出。

### 4.4 單場結算【決議，方向】

一場結束後要有結算，讓「同樣撐到 30 天」的玩家之間還能比較表現（例如撐住的程度、殖民者狀態、太空站發展水準）。結算要呈現哪些指標、怎麼計分由各組決定。

跨場次保存的成就系統與排行榜不在範圍內，見第 6 節。

## 5. 目標玩家與平台【方向】

- 目標玩家：喜歡規劃與管理類遊戲的 PC 玩家，想要比缺氧更短、一次就能玩完的體驗。
- 平台：PC（linux, windows, macOS）、單人、2D。

## 6. 範圍

範圍內只放支撐核心體驗的東西，其餘明確列為範圍外，避免需求失控。

**範圍內**

- 單人遊戲
- 單一太空站地圖，2D
- 少量殖民者，彼此為合作關係
- 支撐第 3 節四項核心體驗的系統
- 第 7 節的結束條件與第 4.4 節的單場結算

**範圍外**【含 v0.1 原列項目，可增刪】

- 流體、氣體、溫度的物理模擬
- 研究／科技樹
- 存檔與跨場次的長期進度（含跨場次成就、排行榜）
- 劇情與對話系統
- 多人連線
- 3D 表現
- 叛徒／殖民者敵對機制（11/07 提到可作為提升難度的手段，但會動到「合作」這個核心假設，先列為範圍外的延伸選項）
- 正式美術與音效（需求階段最多用 wireframe）

**交付物【決議】**

各組的交付物為 **prototype 與相關文件**。

- **prototype**：可執行的原型。prototype 完成即視為該組完成，這也是第 11 節第 1 條「完成」的判準。
- **相關文件**：各組方法論下的需求分析與設計產出，以及第 11 節第 5、7 條要求的 AI 使用紀錄。
- 時程與各階段期限另行公告，不寫入本文件。

## 7. 結束條件【決議】

v0.1 的 8.1「無盡模式」已被否決——組內共識是遊戲要有明確的結束。

- **勝利**：撐過第 30 天。
- **失敗**：過程中任一失敗條件被觸發，當場結束。
- **結算**：不論勝敗都進結算畫面（見 4.4）。

**失敗條件的方向**（具體有幾條、門檻多少由各組決定）：

| 類型 | 說明 | 狀態 |
| --- | --- | --- |
| 太空站毀損 | 基地完整度／毀損度超過可承受範圍 | 一定要有【決議】 |
| 與地球失去聯繫 | 通訊中斷（例如干擾、通訊設施失能） | 建議納入【決議】 |
| 殖民者崩潰 | 殖民者狀態（生存或心理）集體失守 | 建議納入【決議】 |
| 發展落後 | 到某個階段仍未達到最低發展水準 | 選用【決議，待各組判斷】 |

## 8. 危機來源【決議，只定方向】

為了讓三組的分析有共同起點，這裡只定「危機分成哪幾類」，不定機制與數值。各組自行決定要做哪幾種、如何運作。

| 類別 | 討論中提到的例子 |
| --- | --- |
| 外部 | 隕石、太陽風暴、外部干擾造成通訊中斷 |
| 內部 | 設備故障、工業生產的垃圾與廢棄物堆積、衛生惡化導致細菌侵蝕線路 |
| 人 | 殖民者的生理與心理狀態惡化 |

這些例子是方向示意，不是必做清單；各組也可在同類別下提出其他危機，但應能追溯到這份文件的核心體驗。

## 9. 客戶角色

由一位組員扮演客戶（利害關係人），三組都向他訪談需求。

**回答原則**

1. 客戶只描述「想要什麼體驗」，不替各組做設計決定。
2. 本文件沒寫到的問題，客戶依照願景與核心體驗即興回答。
3. 不同組問到同樣的問題時，給一樣的答案。
4. 每次訪談都留紀錄（問題與回答），各組各自保存，作為報告的證據。
5. 客戶本人仍屬於某一組時，在自己組內不提供其他組拿不到的額外資訊。

## 10. 限制條件與協作約定

這一節是專案後勤，不是設計決定，不應限制各組的需求分析結果。

**技術選擇【決議】**

- 引擎：Godot（2D）
- 理由：確定做 2D，Godot 在 2D 上最直接，組內也傾向這個選擇。
- 曾評估：three.js、Unity、Unreal。

**引擎版本與建置設定【決議】**

三組必須一致，否則各組產出之間的差異會混入版本因素，無法當作方法論比較的證據。

| 項目 | 決定 |
| --- | --- |
| 版本 | Godot **4.7.2 stable**，釘到 patch，不是「4.7.x」 |
| 升版 | 專案期間不升版。4.8 可能在期中發布，一律不動 |
| 建置 | standard 版，不使用 .NET 版 |
| 語言 | 只使用 GDScript，不使用 C# |
| Renderer | 固定 Forward+ |
| 視窗 | 解析度與 stretch mode 固定並寫入 `project.godot` |
| 文件連結 | 一律使用 `docs.godotengine.org/en/4.7/`，不使用 `/en/stable/` |

理由：

- 4.7 是目前唯一仍在維護的 stable 系列；4.5、4.6 已不再出修補版。
- 本專題用到的 2D 功能在 4.5 到 4.7 之間幾乎沒有差異，升版沒有代價。
- Windows 自 4.6 起新專案預設 D3D12，不固定 renderer 會造成三組跑在不同後端上，出現「只有某台機器有問題」。
- 4.8 發布後 `/en/stable/` 會改指向，舊連結的意思會無聲改變。

**引擎 API 驗證【決議】**

AI 產出的引擎 API 一律對 Godot 4.7 官方文件驗證，驗不到的標為 unverified。Godot 4.7 發布於 2026-06，晚於多數模型的知識截止，三組會各自撞到同一批過時 API。這類情形依第 11 節第 7 條單獨標記，與 AI-invented requirement 分開統計。

**AI 工具【決議】**

AI 工具的選擇屬各組方法論的一部分，**不統一**。三組各自選用，但必須揭露。

| 項目 | 規定 |
| --- | --- |
| 選用 | 各組自行決定工具、模型，以及是否啟用工具附帶的自動化（hooks、agent 編排等） |
| 揭露 | 須揭露工具名稱與版本（tag 或 commit）、主要使用的模型、啟用了哪些自動化 |
| 位置 | 揭露寫在各組的 AI 使用紀錄，見第 11 節第 5、7 條 |

工具不統一，會讓各組產出的差異同時包含「方法論」與「工具」兩個因素。揭露的目的是讓報告能分辨這兩者，而不是假裝沒有差異。

各組可自行撰寫 workflow 來跑，做法屬各組方法論的一部分，本文件不規定。

**參考（不強制）**

- `Donchitos/Claude-Code-Game-Studios`（MIT）：Claude Code 的遊戲開發模板，含 Godot 專用 agent 與 slash command。
- 評估結果：該模板的 agent、skill 與索引文件交互引用密集。實測砍掉約一半後，掃出 599 處跨檔引用失效，其中 `/help` 依據的 workflow 目錄會靜默指向不存在的指令、不會報錯。要用建議整包保留、只取需要的部分，不要裁剪。
- 注意：該模板的 hooks 會在每次工具呼叫時執行 bash 腳本。

**共用骨架的界線【提案，待三組確認】**

- 共用：`project.godot`（版本、renderer、解析度）與 `.gitignore`。
- 不共用：任何 script、scene、autoload，以及 placeholder 美術。
- 理由：再多就等於替各組預先做了架構與空間設計。共用一組 tileset 會固定 tile 尺寸，而尺寸會往回影響太空站的空間設計。

## 11. 給各組的規則【決議】

三組從同一份文件出發、獨立分析，最後的差異才能當作比較的證據。

1. 本文件是三組唯一的共同輸入；定案後各組獨立進行需求分析，完成前不互相參考產出。「完成」指該組 prototype 完成，見第 6 節交付物。
2. 本文件不加入具體機制與數值。寫到「氧氣每秒減少多少」這種內容就代表越界了。
3. 本文件存放於共用 repo `project-common`，並為其第一個 commit；各組 repo 以本文件為起點，各組產出都應可追溯到本文件。
4. 定案後如需修改，需三組同意，並記在第 12 節的修訂紀錄。
5. 各組從第一天開始記錄 AI 使用（工具、問了什麼、接受或拒絕及原因）與花費時間。
6. 各組在自己的 repo 作業（`group-waterfall`、`group-agile`、`group-AI`），共用內容放在 `project-common`；完成前不讀取其他組的 repo。【提案，待三組確認】
7. 第 5 條的紀錄使用統一欄位：日期／工具／模型／問了什麼／接受或拒絕／理由／工時。另單獨標記「AI 產出過時或不存在的引擎 API」，與 AI-invented requirement 分開統計——前者是版本造成的雜訊，後者才是要比較的現象。【提案，待三組確認】
